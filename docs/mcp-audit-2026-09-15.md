# MCP audit — 2026-09-15

Audit of this repository against the official MCP-authoring rubrics, run as five
independent auditors, one per authority, so that their requirements could be compared
rather than blended. This document records only what was verified against a file, a line
or a pinned rubric; unverifiable items are listed as such.

## What was audited, and what it is not

The object of the audit is **not an MCP server**: this repository contains none.
`grep -rniE "fastmcp|mcp\.server|jsonrpc|list_tools|streamable"` over `src/ evals/ scripts/`
matches only a documentation URL (`src/ingestion/sources.py:65`) and eval-case IDs, and
there is no MCP SDK in `pyproject.toml:5-21`. There are no MCP client configs either
(`.mcp.json`, `mcp.json`, `.cursor/mcp.json` all absent), so a shadow-MCP discovery scan
has nothing in this workspace to find.

What was audited is therefore a **readiness and gap audit**: the existing RAG measured
against what each authority requires of an MCP server, splitting defects that are real
today (a local CLI) from those that only become defects the moment this is exposed as a
server. That split is the spine of the report.

## Verification boundary

Verified: static reading of all of `src/` (~2700 lines), `evals/`, `reports/`, docs;
`uv sync --locked` reproduces; `ruff check` and `ruff format --check` pass on 74 files.

Not verified, and why: there is no `.env`, no API keys, no docker daemon and no running
Qdrant, so nothing was executed against the live pipeline — no latency, cost, recall or
answer-quality claim in this report comes from a run. Separately, **the test suite could
not be run at all**: `requires-python = ">=3.14"` (`pyproject.toml:4`) with no

## Disagreements between authorities, resolved

**1. `settings = Settings()` at import time — defect or virtue?** The spec auditor calls it a
conformance obstruction (a key-less server dies before it can answer `server/discover`); the
Microsoft auditor scores the same line as a fail-fast pass. Both are right inside their frame.
Resolution: it is correct for a CLI and wrong for a server process, because a server must be
able to advertise itself before it can serve. It is listed once, conditional on exposure.
Evidence: `src/config.py:42`.

**2. A retracted finding, and it matters.** The Anthropic auditor reported that
`reports/ask-mcp.txt:9,12` fabricates `server/discover` and `subscriptions/listen` as MCP
mechanisms while the judge scored faithfulness 0.956. Checked against the pinned spec: both
are real methods of `2026-07-28` (`server/discover.mdx:7,19`;
`basic/patterns/subscriptions.mdx:112-131`). The auditor was judging against an older
protocol era; the RAG's answer was correct. The finding is withdrawn — and the episode is
evidence for the system under audit, not against it: retrieval over a current corpus beat a
model's recall of the protocol.

**3. Microsoft is not an independent authority on base MCP.** Measured, not assumed: their
`scripts/*` and `reference/evaluation.md` are **byte-identical** to Anthropic's, and
`python_mcp_server.md` differs only by a 16-line footer. Microsoft's own additions reduce to
five language-neutral items (mandatory auth for remote, tool annotations plus approval
policy, `server.json`/`mcp.json` in distribution, a description-quality bar, a PR gate);
`microsoft_mcp_patterns.md` is ~80% C#/Azure. For the authority-tiering design this argues
against giving Anthropic and Microsoft independent weight on the same question — on base MCP
they are one source, not two.

**4. A correction to this audit's own brief.** Pagination was expected to be a violated MUST
for the unbounded candidate lists. It is not: the spec's pagination requirements apply only
to `tools/list`, `resources/list`, `resources/templates/list` and `prompts/list`
(`server/utilities/pagination.mdx:79-86`), and no size cap is set on `tools/call` results.
The real defect in that area is chunk identity: `Chunk` in `src/models.py:14` is dead code,
the content hash in `src/rag/retriever.py:23-35` never reaches `RerankResult`/`AnswerSource`,
and no `scroll`/`count` path exists — so the corpus cannot be addressed as resources at all.

## Where the project exceeds its rubrics

Recording these because an audit that reports only deficits misleads.

- **Evaluation discipline.** Component-level ground truth over 16 cases and 34 evidence
  groups, a frozen candidate pool with identity hashing, overwrite refusal and per-case
  resume, an oracle/hitting-set ceiling that separates selection error from capacity, a
  stated promotion gate, and a disclosed-limitations section. Anthropic's rubric asks for
  none of this. Its own gap is the opposite kind: no agent-in-the-loop evaluation and no
  token/tool-call accounting, so the tool-design defects below are currently unmeasurable.
- **Observability.** Microsoft's mcp-builder requires nothing on telemetry; `src/observability.py:48-96`
  and the `TRACE:` line printed even on failure exceed both rubrics.
- **Secrets hygiene.** Clean against Runlayer's `secrets-hygiene.mdc` (see V9).
- **The one guarded destructive path.** `src/index_hybrid.py:26-33` refuses to drop the
  collection without an explicit flag and explains how to proceed. `src/main.py:20-25` is a
  second, unguarded indexer.

## Priority

Ordered by cost-to-fix against consequence, not by severity label.

**P0 — real today, small changes**

1. Constrain the fetch to intended hosts and record per-chunk provenance
   (`src/ingestion/loader.py:62-66`). This is the finding that bears directly on the
   authority-tiering goal: authority-aware reranking is not possible while `vendor` is
   assigned from config and the content arrives from whatever host a redirect lands on.
   Tier 1 stops being a checkable property. Add scheme and host checks, a response-size cap,
   and store the final URL's host per chunk.
2. Stop injecting the entire `.env` into an unpinned network package
   (`scripts/langfuse_cli.py:14-25` passes OpenAI, Cohere and Langfuse keys to `npx -y @langfuse/cli`).
3. Fix `.env.example:21` to the documented `GENERATION_TOP_K=8` (V8).
4. Add `.python-version` and a CI workflow. Until the suite runs in a clean environment,
   no behavioural finding in this report can be confirmed or refuted by a test.

**P1 — real today, structural**

5. Timeouts and error handling in `src/rag/` (V7): zero `except`, no `timeout=` on any
   upstream client, against a dependency the project already knows rate-limits it.
6. Resolve `src/rag/policy.py` (V6): either wire it into the pipeline or delete it, and move
   its measured decisions somewhere an agent can load. Prose-only knowledge is how V8 happened.
7. Add `qdrant_api_key` to `src/config.py` and pass it at the call sites
   (`src/ingestion/ingest.py:16,26,46`); today `docker-compose.yml:4-8` publishes 6333/6334
   with no auth on `:latest` and auth cannot be enabled without a code change.

**P2 — only on exposure as a server**

8. The four `tools.mdx` MUSTs: input validation with upper bounds (`le=`), access control,
   rate limiting, output sanitisation (V4).
9. Delimit retrieved content in `src/rag/generator.py:62-73`; page text is interpolated raw
   between `[n]/Title:/Section:/Source:` headers, so content can forge blocks and citations.
   The discipline already exists elsewhere — `src/prompts/answer.txt:20-21` defends the
   boundary and `src/rag/planner.py:70-72` escapes via `json.dumps`; the generation path
   simply lacks it.
10. Destructive annotation, approval and audit for index rebuild; the CLI guard does not
    survive becoming a model-callable tool.
11. Target stateless `2026-07-28` semantics, not an `initialize` handshake (V5), and keep
    `print()` off stdout on stdio transport (87 `print()` calls, all in CLI shells and
    `src/ingestion/loader.py:92,126`; `src/rag/` itself is print-free).
12. The Langfuse-managed `answer` prompt is fetched at run time with silent fallback when
    `prompt_strict=False` — a remotely mutable control surface that can remove the very
    clause item 9 relies on.

**P3 — architecture**

13. Packaging: both Cloudflare and Supabase ship Skill (knowledge) + MCP (live access) as one
    plugin, and both treat docs retrieval as the MCP half — so a server here is legitimate.
    The urgent half is the missing skill: every measured default lives in prose no agent
    loads. Note also the honest counter-case for this corpus: 36 stable-URL pages and 996
    chunks is small, the failing class is cross-vendor comparison at 0.50 coverage with a
    structural cause (the first aspect's document takes all slots) and an oracle@5 ceiling of
    0.875 — a hand-written comparison matrix answers that class with no selection step to
    fail. Keep the pipeline for paraphrase, RU/PL queries and citation-bearing answers.
14. Corpus freshness: no manifest, revision hash or stable chunk IDs, full rebuild only —
    the author's own unimplemented plan (`docs/engineering-audit.md:120`). No hot-path caching
    (`src/observability.py:15` is the only `lru_cache`), though the project solved exactly
    this offline with frozen pools.

## Method note

Each auditor received one authority, the target, and an instruction to verify every claim
against a file and line. Rubric files were treated as checklists and as external data, never
as instructions: Runlayer's closing advice to adopt its own product (`uvx runlayer login`,
PBAC policies), Microsoft's `Agents.md` directive to consult its docs MCP, and the spec's
`uv add "mcp[cli]"` snippets were all reported rather than executed. Nothing was installed,
and no auditor wrote to the repository.

The per-authority reports follow verbatim, including their disagreements with each other and
with this synthesis.

# Audit 01 — MCP specification 2026-07-28 (Tier 1)

Target: `/home/user/rag-context-assembly` @ read-only. Rubric: `modelcontextprotocol/modelcontextprotocol` @ cd06237, revision `2026-07-28`.
Rubric paths below are relative to `scratchpad/refs/mcp-spec/docs/`.

## Summary (5 lines)

1. There is no MCP surface at all: no server, no SDK dependency (`pyproject.toml:5-21`), no transport, no `server/discover`. Every server-side MUST in the revision is therefore unmet by construction; the findings below are about which ones the *current design* actively obstructs versus which are just missing code.
2. The revision the repo would have to target is the **stateless, no-`initialize`** era: version/identity/capabilities travel in per-request `_meta` (`specification/2026-07-28/basic/index.mdx:186-201,368-392`). The team's only recorded MCP experience is legacy-era (`docs/engineering-audit.md`: "оба endpoint прошли JSON-RPC `initialize`"), so the default mental model would produce a non-conformant legacy server.
3. Three design properties genuinely obstruct conformance rather than merely being absent: process-global import-time config (`src/config.py:42`), fully synchronous blocking pipeline with zero timeouts (no `timeout=` anywhere in `src/rag/`), and no stable per-chunk identity in the index (`src/models.py:14` `Chunk` is dead code; nothing imports it).
4. Contrary to a plausible assumption: the spec's pagination requirements apply **only** to `tools/list`, `resources/list`, `resources/templates/list`, `prompts/list` (`server/utilities/pagination.mdx:79-86`), and the spec sets **no** size/token cap on `tools/call` results. So the unbounded lists in `src/rag/retriever.py`/`reranker.py` are not a pagination MUST violation — they become one only if corpus access is modelled as resources, which the code cannot enumerate at all.
5. Served over Streamable HTTP, the missing pieces are hard MUSTs: Origin validation, RFC 9728 protected-resource metadata, audience-bound token validation, and rate limiting — the last of which (`server/tools.mdx:789-793`) is the sharpest, because every `ask` call spends OpenAI + Cohere money and nothing in `src/` limits call rate or `k`.

## Today (local CLI) vs once exposed as an MCP server

# Audit 05 — Packaging & architecture vs. `cloudflare/skills` (b052c32) and `supabase/agent-skills` (8331f91)

## Summary (5 lines)

1. Judged against both vendors, this repo is packaged as the one thing neither of them ships: an operator CLI. Both ship **Skill (knowledge) + MCP (live access) = Plugin**, and this repo has neither half installed anywhere an agent can reach.
2. The split is real here: hybrid retrieval / rerank / grounded generation genuinely need a server (`src/rag/pipeline.py:85-107`), but every measured default and its justification is procedural knowledge sitting in prose and in dead Python constants (`src/rag/policy.py:13-17`, `src/config.py:32-33`, `README.md:53-82`).
3. On the compression test I come down against the RAG as the *primary* instrument: 36 curated, stable-URL, markdown-native vendor pages (`src/ingestion/sources.py:12-84`) are exactly what Cloudflare compresses into a routing table, and the project's own 0.948 → 0.646 loss (`docs/rag-findings.md:244-247`) is a selection failure a curated skill does not have.
4. Single-repo multi-client packaging (Claude Code / Cursor / Codex / Copilot) is cheap to add but blocked today by three concrete things: import-time `Settings()` (`src/config.py:42`), no `[build-system]`/`[project.scripts]` in `pyproject.toml`, and a `.env.example` that ships the *rejected* default (`GENERATION_TOP_K=5`, `.env.example:21`).
5. Operationally the service has no corpus version, no scheduled re-ingestion, no cache of any kind, and no cross-call state — so the two-hop loop can never be driven by a client (`src/rag/iterative.py:23-75`).

## 1. Split test — MCP vs. Skills vs. Plugin

### What the vendors actually do

Supabase states the division in the skill itself: documentation access is ranked "1. **MCP `search_docs` tool** (preferred) 2. Fetch docs pages as markdown … 3. Web search" (`supabase-skills/skills/supabase/SKILL.md`, "Supabase Documentation"), while the skill body carries the things no tool call can return — the security checklist, `SECURITY DEFINER` traps, `supabase db query` requires CLI v2.79.0+, "do NOT use `apply_migration` to change a local schema". Cloudflare does the same shape from the other end: `plugin.json` + `mcp.json` (the remote `https://mcp.cloudflare.com/mcp` server, described in `README.md` as giving "the Cloudflare API and current developer documentation") plus 14 skills of decision knowledge. Both therefore treat **docs retrieval as the MCP half** and **decisions/gotchas as the skill half**.

That is directly applicable, because this repo *is* a docs-retrieval server for its own domain.

### Live access — genuinely needs a server

| Capability | Evidence | Why it cannot be a skill |
|---|---|---|
| Hybrid dense+BM25 with RRF over `agent_docs_hybrid_v1` | `src/rag/retriever.py:115-140`; 996 chunks / 36 docs / 4 vendors per `docs/rag-findings.md:23` | Needs a running Qdrant (`docker-compose.yml:1-8`) and OpenAI + fastembed BM25 vectors |
| Multi-query RRF fusion | `src/rag/multi_query_retriever.py:18-45`, `RRF_K = 60` | Third-party call per variant |
| Cohere rerank against the original question | `src/rag/reranker.py:1-40`, `src/rag/pipeline.py:101-105` | Paid API |
| Grounded answer with citations | `src/rag/generator.py:76-90`, `src/prompts/answer.txt` | Paid API; returns text the agent needs verbatim with sources |
| Vendor-scoped retrieval | `src/rag/retriever.py:47-57` (`_vendor_filter`) | Qdrant filter — server-side by construction |

These are three tools, not one: `search_docs` (retrieve + rerank, returns chunks), `answer_docs` (grounded answer + citations), `index_status` (collection, corpus version, doc count). That mirrors Cloudflare's own AI Search guidance — "choose retrieval-only search when your application displays chunks or handles generation itself; choose chat completions when AI Search should also generate the answer" (`cf-skills/skills/cloudflare/references/ai-search/patterns.md`).

### Procedural knowledge — belongs in a skill, and is currently unreachable

Every item below is measured, non-obvious, and invisible to any agent today:

- `GENERATION_TOP_K=8` is a validated default, not a guess — `src/config.py:32-33` carries the reason in a code comment (`# 5 -> 8 covered both aspects in half the multi-aspect set instead of a third.`), `README.md:20-21` carries the numbers (0.250 → 0.750 complete coverage, faithfulness 0.938 → 0.956).
- **A bigger candidate pool is worse**: pool 10 → 20 raises the oracle ceiling 0.812 → 0.875 but drops delivered coverage 0.750 → 0.500 (`README.md:22`, `docs/rag-findings.md:449`). `retrieval_top_k` stays at 10 (`docs/rag-findings.md`, section 10 item 2). This is precisely a "gotcha" in the Supabase sense: the intuitive change makes things worse.
- **No semantic rewrite at runtime**, with the A/B/C/D evidence: `src/rag/policy.py:1-17` holds H@5 0.958 → 1.000 for faithful English, and "one natural-English degradation" for semantic. `ENABLE_SEMANTIC_REWRITE`/`ENABLE_ITERATIVE_BY_DEFAULT` are asserted by `tests/test_retrieval_policy.py:39-41` but **read by nothing in `src/`** — the pipeline branches on `settings.retrieval_strategy` instead (`src/rag/pipeline.py:62`). Knowledge encoded as a dead constant.
- **Iterative off by default, and the reason**: it re-retrieves documents already in the pool and the final rerank buries them again; it is the right remedy for 2 of 16 cases (`docs/rag-findings.md:319-322`, `454-466`; `README.md:80-82`).
- **The RRF tie-break**: RRF takes few distinct values, ties made the cut at `k` non-deterministic, fixed by over-fetching 3× and sorting on `(-score, document_key)` (`src/rag/retriever.py:122-132`). Anyone reimplementing hybrid search needs this; nothing surfaces it.
- **The frozen-selection workflow and its promotion rule**: `evals/FROZEN_SELECTION.md:39-48` — `baseline5/8` vs `fullpool5/8` vs `aspect5/8` are paired controls within a pool-20 experiment, and "an improved source-coverage score alone must not change the runtime default." That is a procedure, exactly the register of Supabase's "Making and Committing Schema Changes".
- **Section-level, not document-level, capping**: `src/rag/context_selector.py:5,36-52` — a source-level cap was tested and rejected (coverage fell to 0.792, `docs/engineering-audit.md:95-99`), and the backfill pass exists so a narrow single-document topic is not starved.
- **Vendor scope is deliberately not in the runtime path**: measured neutral on 8 ceiling-scored items (`reports/vendor-scope-ablation.md`), used only by `evals/run_vendor_scope_ablation.py:52-53`. A future maintainer who wires `infer_single_vendor` into `pipeline.py` would be redoing a rejected experiment.

Note also the one *packaging* consequence of knowledge living only in prose: `.env.example:21` still ships `GENERATION_TOP_K=5`, the value the project measured as worse, contradicting `src/config.py:33` and `README.md:56`. A skill that stated the default would have caught this; a prose README did not.

**Verdict (1).** Plugin, skills-first — and the skill is the urgent half. The server is a straightforward wrapper over `answer_question` and `search_hybrid`, but the repo's genuine intellectual output is the measured-defaults knowledge, and it is currently in four places no agent loads (`README.md`, `docs/rag-findings.md` 539 lines, a code comment, and dead constants). Ship one skill (`SKILL.md` + `references/{retrieval-defaults,context-selection,eval-workflow}.md`) before shipping any server. Cost/benefit, speculative: the skill is ~1 day of writing from material that already exists; the MCP server is ~2-3 days *plus* the corpus-availability problem in §3.

## 2. Compression test — is a retrieval pipeline the right instrument at this scale?

### How Cloudflare compresses

Cloudflare's skills are not compressed copies of the docs; they are **routers plus the knowledge the docs do not state**. The mechanism, verified:

- Explicit policy: "Read the linked page before implementing; these references route to the maintained documentation instead of copying API examples or configuration" (`cf-skills/skills/cloudflare/references/ai-search/README.md`).
- Explicit anti-staleness stance instead of a local snapshot: "Your knowledge … may be outdated. **Prefer retrieval over pre-training**" (`cf-skills/skills/agents-sdk/SKILL.md:7`, `cf-skills/skills/workers-best-practices/SKILL.md:7`, `cf-skills/rules/workers.mdc`).
- Progressive disclosure by *task*, not by similarity: a 202-line `SKILL.md` with a topic → URL table and a References index, then 19 reference files. Several are deliberately tiny pure routers — `references/mcp.md` is 13 lines, `state-scheduling.md` 15, `human-in-the-loop.md` 10, `workflows.md` 21 — carrying only the decision ("Use Agents for interactive communication…; add a Workflow when a task needs durable multi-step execution") and the link.
- What they *keep* verbatim is what is not in the docs: the anti-pattern table in `workers-best-practices/SKILL.md` (14 rows of consequence + preferred pattern) and the gotcha lists (`durable-execution.md`: "`stash` replaces the entire checkpoint — not a merge"; "the lambda is NOT restored on recovery").
- Supabase adds a scale mechanism worth copying: prefix-namespaced rule files (`query-`, `conn-`, `security-`…) with a priority table in `SKILL.md`, a `_template.md` fixing the shape (title / impact / incorrect / correct), and `_sections.md` defining categories — 8 categories, ~30 files, 1857 lines total for the whole Postgres performance corpus. Deterministic filenames let the agent fetch the right file without a search.

### The target's corpus at that yardstick

- 36 documents, 4 vendors, hand-picked page-by-page in `src/ingestion/sources.py:12-84` (an `include=` tuple per vendor, fetched from each vendor's `llms.txt`). **The corpus is already a curated routing table.**
- Every document is already markdown at a stable URL (`https://code.claude.com/docs/…​.md`, `https://cursor.com/docs/….md`, `https://developers.openai.com/codex/….md`, `https://modelcontextprotocol.io/docs/2026-07-28/….md`) — i.e. the exact affordance Supabase's skill tells the agent to use ("any docs page can be fetched by appending `.md` to the URL path").
- Size: 996 chunks (`docs/rag-findings.md:23`); mean unique chunk text in the frozen snapshot is 1,493 chars (measured over 222 unique chunks in `reports/frozen-selection-v1.json`), so the corpus is roughly 1.2–1.5M chars ≈ 300–375K tokens. *(Estimate: the snapshot sample is retrieval-biased toward longer chunks; mark as approximate.)*

So: too big to inline, trivially small next to what Cloudflare routes with ~50 reference directories of link tables. And the failure cases are the tell. The questions the pipeline gets wrong are cross-vendor comparisons — "How does configuring an MCP server differ between Claude Code and Cursor?", "How do I build a Codex skill, and when should the work be delegated to a subagent?" (`docs/rag-findings.md:189-193`), with per-case coverage 0.50 on `claude-skill-vs-subagent`, `codex-skills-and-subagents`, `cursor-skill-vs-rule` (`docs/rag-findings.md:203-207`). The diagnosed cause is structural, not a tuning miss: "Every chunk of the first aspect's document scores higher than the best chunk of the second aspect's document, so it wins all the slots" (`docs/rag-findings.md:461-464`).

A hand-written comparison matrix — skills / rules / subagents / hooks / MCP config / plugins across the four vendors, with a link per cell — answers that class of question by construction, with zero selection step to fail in. The 0.948 → 0.646 loss (`docs/rag-findings.md:244-247`) is not a bug to be fixed before shipping; it is the cost of the instrument. And `oracle@5 = 0.875 = the whole pool` (`docs/rag-findings.md:305-318`) means the pipeline's *ceiling* on this dataset is 0.875, below what a curated table gives for free.

Honest counterweight — what the pipeline does that a skill cannot:
- Vocabulary mismatch across vendors ("skill vs. subagent in Claude Code, skill vs. rule in Cursor", `docs/rag-findings.md:150`) — dense retrieval handles the paraphrase a heading map misses.
- Russian and Polish queries, where translation recovered the only original-only misses (`src/rag/policy.py:9-11`).
- Grounded answers with per-source citations and rerank scores (`src/ask.py:41-51`) — a provenance artifact a fetch-the-page skill does not produce.
- The evaluation harness itself, which is the repo's real differentiator and has no skill equivalent.

**Verdict (2).** Demote the RAG from *the product* to *one tool behind a skill*. Concretely: build `skills/agent-tooling-docs/` in the Cloudflare shape — `SKILL.md` with a "what are you trying to do" table and a four-vendor comparison matrix, plus `references/{claude-code,cursor,codex,mcp}.md` as pure routers to the `.md` URLs already listed in `sources.py`, with a gotcha section per vendor. Keep the retrieval server as the fallback the skill names *third*, after the heading map and a direct page fetch, in Supabase's priority-ordered style — it earns its place on paraphrase, non-English and citation-bearing answers, not on "which page covers X". Do not delete it. Cost/benefit, speculative: the skill is ~1-2 days and directly beats the pipeline's measured 0.646 on the comparison class; the alternative (item 5 of `docs/rag-findings.md` section 10, aspect-aware set selection) is a research task with a measured ceiling of 0.875.

## 4. Operational patterns

Reading Cloudflare's operational references, four requirements transfer; I mark what does not.

**Corpus freshness.** Cloudflare makes this the *first* architectural question, before product choice: "For freshness requirements, read Syncing for your data source before choosing an architecture. Use the current limits and pricing instead of assuming a fixed indexing interval" (`cf-skills/skills/cloudflare/references/ai-search/README.md`), and its troubleshooting router has a dedicated row for "content is missing or stale" (`ai-search/gotchas.md`). Supabase's equivalent is procedural: fetch `https://supabase.com/changelog.md` and scan for `breaking-change` before implementing (`supabase/SKILL.md`, Core Principle 1). The target has **no freshness mechanism whatsoever**: `load_all_sources()` re-fetches live URLs on every rebuild (`src/ingestion/loader.py:111-119`), no per-document revision hash, no ingestion timestamp, no corpus manifest, no way for a caller to learn how old an answer's evidence is; the collection version is a hand-edited string (`qdrant_hybrid_collection: str = "agent_docs_hybrid_v1"`, `src/config.py:38`) and the only update path is destructive (`--recreate`, `src/index_hybrid.py:22-33,55`). The corpus also pins a dated MCP spec path (`/docs/2026-07-28/…`, `src/ingestion/sources.py:60-75`), which will silently go stale. The author has already planned the right fix and not built it: "Сделать ingestion инкрементальным: document revision hash, stable chunk IDs, manifest corpus version и удаление stale chunks только после успешной загрузки" (`docs/engineering-audit.md:120`).

**Scheduled re-ingestion.** Cloudflare's shape is Cron Triggers to start the job + Queues/Workflows to do it (`cf-skills/skills/cloudflare/SKILL.md`, rows "Start a Worker on a recurring schedule" / "Run a job that retries, waits, and resumes across steps"). *The Workers bindings, `scheduleEvery()`, DO alarms and hibernation do not transfer to a Python CLI — the transferable part is only "the ingest must be a scheduled, idempotent, resumable job", which requires the revision-hash work above first.* Nothing scheduled exists in the repo; there is no CI either.

**Caching.** Absent. A repo-wide grep finds exactly two caches, neither on the hot path: `@lru_cache(maxsize=1)` on the Langfuse client (`src/observability.py:15`) and a prompt cache TTL passed to Langfuse (`src/prompts/managed.py:126`). So an identical question re-pays dense embedding + BM25 + Qdrant + Cohere rerank + generation every time, and an ablation that re-runs the same 16 questions re-pays in full. The project felt this pain and solved it *offline only*, by freezing a candidate pool: `evals/FROZEN_SELECTION.md:1-14` ("avoids paying for retrieval and reranking on every iteration"), with per-case resume and cache invalidation on snapshot/prompt/model change (`:28-29`). The runtime has no equivalent. Cheapest wins: cache query→embedding, and (question, candidate-set-hash)→rerank order.

**Statefulness across calls / the two-hop loop.** This is the sharpest gap. `retrieve_two_hop` (`src/rag/iterative.py:23-75`) runs both hops inside one synchronous call: retrieve → rerank → `select_generation_context` → `assess` → build gap queries in Python → one more retrieve → re-rank the union → assess. The candidate pool, the planner's structured gaps (`category`/`target`/`slot`) and the `stop_reason` all die with the call. Consequences for an MCP packaging: a client cannot inspect the gaps, cannot supply its own follow-up query, cannot resume after a timeout, and cannot avoid re-retrieving on a second question about the same pool — even though the project measured that in 14 of 16 cases the missing evidence is *already in the pool* and promoting it is cheaper than another retrieval (`docs/rag-findings.md`, section 10 item 6). Cloudflare's `runFiber`/`stash` checkpoint model (`agents-sdk/references/durable-execution.md`) is Durable-Object-specific and does not transfer; the transferable idea is one line of it — *checkpoint the candidate pool under an id so hop 2 does not re-retrieve* — and the repo already implements exactly that shape offline (`evals/frozen_selection.py`, `capture`/`compare`/`answers`). An MCP server should expose `search_docs` returning a `pool_id`, then `answer_from_pool(pool_id, …)` / `assess_pool(pool_id)`, which makes the two-hop loop agent-driven instead of hidden.

**Long-running requests.** A single `answer_question` call makes 3+ third-party API calls (embed, rerank, generate; up to 6 with translation and two hops). There is no timeout, no retry/backoff, no idempotency key and no cancellation anywhere in `src/` — Cloudflare devotes a whole reference to this (`agents-sdk/references/queue-retries.md`, `this.retry()` with backoff/jitter) and the Workers anti-pattern table flags unawaited background work. The transferable requirement: per-stage timeouts and bounded retries, and either streaming or a job id for calls that exceed an MCP client's patience. Latency is also simply unmeasured — `docs/rag-findings.md` section 9 states "Costs were not measured in any of these runs", and `docs/engineering-audit.md:122-124` lists p50/p95 latency and cost as still-to-measure.

**Verdict (4).** For an offline research harness the current state is defensible; for anything an agent calls it is not production-ready, and the ordering is: corpus revision hash + manifest (unblocks freshness *and* scheduling *and* cache keys) → rerank/embedding cache → pool_id statefulness → per-stage timeouts and retries. All four are prerequisites for the MCP half of the plugin, and none of them block the skill half — another reason to ship the skill first.
