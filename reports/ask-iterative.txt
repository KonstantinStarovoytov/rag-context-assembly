Для такого плагина удобно разделить систему на три уровня:

1. **Skill — сценарий и знания**
2. **Subagents — специализированные расследователи**
3. **Orchestration — координатор выполнения**

## 1. Skills: что и как расследовать

Skill — это Markdown-файл с инструкциями, знаниями и повторяемым workflow. Его можно вызвать явно, например `/investigate-failure`, или Claude может загрузить его автоматически, когда запрос релевантен. [1][3][4]

Для расследования падений тестов основной skill может:

- принимать ссылку на CI job, лог или stack trace;
- классифицировать ошибку;
- определять, какие subagents нужно запустить;
- задавать формат итогового отчёта;
- описывать правила доказательности: отделять факт от гипотезы;
- рекомендовать следующие проверки;
- при необходимости запускать воспроизведение теста.

Например:

```text
/investigate-failure

1. Собери входные данные:
   - test name
   - error and stack trace
   - CI job metadata
   - changed files
   - relevant logs

2. Определи тип сбоя:
   - product defect
   - test defect
   - flaky test
   - environment/dependency issue
   - timeout/resource issue

3. Запусти подходящих subagents.

4. Сведи результаты:
   - root cause
   - evidence
   - confidence
   - suggested fix
   - missing information
```

Skill не должен содержать отдельную экспертизу для каждого типа ошибки, если эта экспертиза нужна только специализированному исполнителю. Его задача — описать общий процесс и критерии результата.

## 2. Subagents: изолированные специализированные задачи

Subagent выполняет задачу в изолированном контексте и возвращает сводный результат. Это подходит для изоляции контекста, параллельной работы и специализированных workers. [3][4]

Возможная структура:

```text
agents/
├── log-analyzer.md
├── code-tracer.md
├── reproducer.md
├── flaky-test-investigator.md
└── environment-investigator.md
```

Их роли могут быть такими:

- **log-analyzer** — извлекает факты из логов и stack trace;
- **code-tracer** — прослеживает путь выполнения от теста до места сбоя;
- **reproducer** — пытается воспроизвести падение и фиксирует команду и результат;
- **flaky-test-investigator** — ищет признаки гонок, зависимости от времени, порядка тестов и нестабильной инфраструктуры;
- **environment-investigator** — проверяет версии, конфигурацию и различия между локальным запуском и CI.

Каждый subagent должен иметь узкий контракт:

```text
Input:
- test name
- failure log
- repository path
- CI metadata

Output:
- findings
- evidence with file/line or log reference
- hypotheses
- confidence
- unresolved questions
```

Полезно требовать, чтобы subagents возвращали не полный поток рассуждений, а структурированный отчёт. Это соответствует назначению subagents: они работают отдельно и возвращают summarized results. [4]

## 3. Orchestration: кто решает, кого запускать

Оркестрация — это слой, который:

- принимает общий запрос;
- выбирает subagents;
- запускает независимые проверки параллельно;
- передаёт результаты финальному синтезатору;
- разрешает противоречия;
- формирует единый отчёт.

В простом варианте оркестратором может быть основной skill:

```text
investigate-failure
├── log-analyzer
├── code-tracer
├── reproducer
└── flaky-test-investigator
```

Связка «skill + subagents» прямо приведена в документации как подход, при котором skill запускает subagents для параллельной работы. [2]

Если задач становится много или результаты нужно перепроверять, используйте dynamic workflow: документация описывает его как скрипт, который Claude пишет для запуска множества subagents в фоне, включая cross-check результатов. [3][4]

Практически можно использовать два режима:

### Быстрый режим

Для одного падения:

```text
log-analyzer
code-tracer
reproducer
→ final synthesis
```

### Глубокий режим

Для сложного или нестабильного падения:

```text
log-analyzer
code-tracer
reproducer
flaky-test-investigator
environment-investigator
→ evidence checker
→ final synthesis
```

## Рекомендуемая структура plugin

Плагин может объединять эти компоненты: SDK поддерживает plugins с skills, agents, hooks и MCP servers. [1]

```text
failure-investigator/
├── .claude-plugin/
│   └── plugin.json
├── skills/
│   └── investigate-failure/
│       └── SKILL.md
├── agents/
│   ├── log-analyzer.md
│   ├── code-tracer.md
│   ├── reproducer.md
│   ├── flaky-test-investigator.md
│   └── environment-investigator.md
├── hooks/
│   └── ...
└── mcp/
    └── ...
```

Дополнительные компоненты:

- **MCP** — если нужно подключаться к CI, системе тест-репортов, issue tracker или хранилищу логов. MCP отвечает за внешнее подключение, а skill — за правильный способ его использования. [2]
- **Hooks** — если расследование нужно автоматически запускать на событие жизненного цикла, например после определённого действия. Hooks предназначены для автоматизации и обработки событий. [1][2][3]
- **CLAUDE.md** — для постоянных правил проекта, например команды запуска тестов, package manager и соглашения по репозиторию; повторяемый workflow лучше оставлять в skill. [2][3][4]

## Короткое правило выбора

| Компонент | Ответ на вопрос |
|---|---|
| Skill | «Как в целом расследовать этот класс задач?» |
| Subagent | «Кто специализированно проверит конкретный аспект?» |
| Orchestration | «Какие проверки запустить, в каком порядке и как объединить результаты?» |
| MCP | «Откуда получить внешние данные или каким внешним инструментом воспользоваться?» |
| Hook | «На какое событие запускать автоматизацию?» |

## Что касается Cursor

Предоставленная документация описывает плагины и Agent SDK Claude, но не описывает модель plugins, skills, subagents или orchestration в Cursor. Поэтому нельзя утверждать на основании этих источников, что указанная структура напрямую поддерживается Cursor.

Архитектурное разделение можно сохранить при переносе:

```text
workflow / skill → worker agents → coordinator
```

Но формат упаковки, механизм регистрации, вызова subagents и интеграции с Cursor нужно отдельно проверить по документации Cursor.
