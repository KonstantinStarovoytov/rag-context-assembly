# RAG pipeline review against six authoritative sources — 2026-09-16

Six independent audits, one source each: Anthropic Contextual Retrieval;
Wang et al. 2024 (arXiv 2407.01219); Microsoft Azure RAG design guide; Chroma
Evaluating Chunking; Chroma Context Rot; Databricks Long Context RAG. Findings
were merged; the count of sources raising the same point is the main ranking
signal, weighted by measured facts about this corpus.

## Facts established during the audit (measured, not estimated)
- Corpus: 35 pages, 308k tokens, 1127 chunks. Above Anthropic's 200k
  "just put it in the prompt" threshold → RAG is justified. Per vendor:
  60–100k tokens (below the threshold).
- Chunk sizes: median 354 tokens, mean 366, p75 522, p90 637, max 955.
  31 % of chunks hit the 3000-char cap (mechanical split of long sections);
  22 % are under 1000 chars. ≈5.1 chars/token (code-heavy markdown).
- Generation context at k=8: ~2.8k tokens median (not the 6k assumed).
- Retrieval eval sets are at ceiling: Hit@5 = 1.0 (48 queries), vendor-scope
  H@1 = 1.0. No precision@k / NDCG anywhere; no negative (unanswerable)
  questions; judge = generator model.
- Index contains boilerplate: every Claude Code page starts with a
  "Documentation Index … llms.txt" blockquote that becomes its own chunk
  (~17 junk chunks); MDX tags (<Tab>, <Note>, <Step>, <Tip>, <CodeGroup>,
  theme={null}) survive into chunks.
- `Chunk.embedding_text` in src/models.py is dead code; what is embedded and
  BM25-indexed is the bare chunk text (headers only for the first chunk of a
  section, no document title or product).

## Ranked findings

### 1. Measurement is at ceiling — nothing below can be verified (Высокий)
Raised by: Azure, Databricks, Anthropic (blocking for #2, #4, #5).
- No negative/out-of-scope questions; `answer.txt:7` requires abstention but
  no eval measures it. `evals/questions.json` is empty.
- Only hit@k and MRR (`evals/evaluators.py:53-141`); no precision@k, NDCG.
  Precision@8 is the one metric still able to move.
- Judge has no failure-mode label (refusal / empty / repeated / summarised
  instead of answered — Databricks App. F); an abstention where the answer
  exists scores as "faithful" (`answer-evaluator.txt:9-10`).
- Judge and generator are the same model; ground truth single-author.
Fix: 10–15 negative questions + `abstain_correct`; `precision_at_k`,
`ndcg_at_k` (~40 lines); `failure_mode` field in the judge; retrieval-only
coverage curve over pool ∈ {5,10,15,20,30} in `probe_context_assembly.py`;
switch judge model. Effort ~1–2 days, cost ≈ $0 (retrieval-only) to a few $.

### 2. Contextual prefix in the embedded/BM25 text (Высокий)
Raised by: Anthropic (#1), Azure (#3a), Chroma chunking (#2).
Chunks 2..n of long sections (Hooks reference: 152 chunks) are indexed without
their heading; no chunk carries product/document name. Cross-vendor homonyms
(hooks, mcp, plugins, rules) are indistinguishable for BM25 at candidate
selection; only the reranker sees Title/Section/Product
(`reranker.py:119-138`). Anthropic: contextual embeddings −35 % failures,
+BM25 −49 %.
Fix, step 1 (no LLM): prepend `vendor / product / title > h1 > h2 > h3` to
`page_content` at index time, keep raw text in metadata for the generator
(`chunker.py`, `generator.py`). New collection. ~2 h + reindex ($0.01).
Step 2: LLM-generated 50–100-token context per chunk in `reindex.py`, cached
by fingerprint, document as cacheable prefix. ~1 day, <$1 per full index.
Needs #1 first: current sets cannot show the gain.

### 3. Clean the markdown before chunking (Средний, cheap)
Raised by: Azure.
Strip the leading "Documentation Index / llms.txt" blockquote (Claude Code,
Codex), MDX tags, `theme={null}`. ~1.5 % junk chunks that BM25 can surface on
"documentation". Include a chunker version in `reindex.fingerprint()` so the
change triggers a reindex. 2–3 h + unit test on three real page headers.

### 4. Distractor control (Средний)
Raised by: Context Rot (#1–3), Databricks (#5), Chroma chunking (#1).
a) `search_docs` skips Cohere rerank (`core.py:126-138`): ranks 11–20 are an
   RRF tail with ties; detailed×20 ≈ 15k tokens of weakly ordered text into
   the caller. Fix: rerank in `core.search` (3–5 lines, +~1 s, Cohere quota).
b) No relevance threshold: 8 slots always filled, backfill ignores score
   (`context_selector.py:34-53`). Own data (§7.5) show k=8 helps multi-aspect
   questions, so threshold only for the backfill pass; needs single-topic
   questions in the eval (#1). ~20 lines + eval.
c) Overlap duplicates: adjacent chunks share 300 chars; selector dedups by
   section, not text. Fix: drop overlap (see #5) or trim it at
   `_format_context`.

### 5. Chunk-size tail and overlap (Средний, experiment)
Raised by: Chroma chunking, Wang, Azure, Anthropic.
Median is already in the strong 200–400-token zone; the problem is the p75+
tail (520–955 tokens) and useless overlap. Own reports say retrieval misses
are "not a chunking defect", so treat as an experiment, not a fix:
configs 3000/300 (current), 3000/0, 2000/0, 1000/0, 2000/0+prefix(#2); one
Qdrant collection each; metrics evidence_coverage, precision@8,
context_utilization, context tokens; <$10, ~0.5 day. Watch "crowding": more
chunks per hooks.md may worsen selected-8 coverage (§7.6).

### 6. Chunk order in the prompt: reverse repacking (Низкий)
Raised by: Wang (#1). Currently forward (`context_selector.py:24`,
`generator.py:44-73`). Wang: reverse best (0.560). At 2.8k tokens and a 2026
model the effect is likely within ±1-case noise. A/B in `_format_context`
keeping citation numbers = rerank rank; 1 h + one eval run; adopt only on
≥2-case gain.

### 7. k sweep on frozen candidates (Низкий, cheap)
Raised by: Databricks (#3). generation_top_k 4/6/8/10 on frozen candidates
(k=12 ≡ 10 with retrieval_top_k=10). Own probe data predict a plateau at
8–10; run it after #1 adds failure_mode, to see whether refusal/summarising
grows with k. A few $, half a day with repeats.

### 8. Prompt: one line about ignoring off-topic passages (Низкий)
Raised by: Context Rot (#4). `answer.txt` covers "say when missing" but not
"some passages are adjacent-topic — do not use or cite them". New Langfuse
prompt version, no deploy.

## Considered and rejected for this project
- Query classification "needs retrieval?" (Wang) — every question here needs it.
- HyDE, query rewriting, Recomp/summarisation, generator fine-tuning (Wang) —
  own A/B/C/D already rejected rewriting; nothing to gain at Hit@5 = 1.0.
- Hybrid α-weighting instead of RRF (Wang) — α=0.3 is benchmark-specific;
  RRF + tie-break works; revisit only on measured misses.
- Embedding model swap — no metric can show the difference yet.
- top-20 into the generator (Anthropic) — own §7.6 measured it worse here.
- Shuffling context (Context Rot) — the context is already 8 disjoint
  sections; shuffling breaks citation numbering.
- "Whole vendor in the prompt with caching" (Anthropic) — per-vendor slices
  are <200k tokens, so it is a legitimate experiment for single-vendor
  questions (removes the selection stage that is the measured bottleneck),
  but 60–100k tokens per request, citation redesign, Context Rot risk. Not a
  default; optional experiment after #1.
- GraphRAG — global questions over 35 pages do not exist.

## Already matching the sources (all six agree)
Hybrid dense+BM25 with RRF and deterministic tie-break; Cohere rerank against
the original question; header-aware chunking; small, measured generation
context (5→8 measured with faithfulness); multi-query with faithful
translation; query rewriting rejected by data; iterative round measured as
useless and kept opt-in; MCP concise/detailed defaults with token cost in the
description; incremental reindex with retrieval smoke check; experiments
logged with config and decision in reports/.

## Suggested order
1 (measurement) → 3 (cleaning) → 2 step 1 (static prefix) → 4a (rerank in
search_docs) → 5 (chunk experiment) → 2 step 2 → 4b/6/7/8 as data allows.

### Negative set (`rag/negative-v1`, 12 out-of-corpus questions)
Run: negative-abstention-k5, https://cloud.langfuse.com/project/cmtogb8i90jw1ad0i9i6g2tae/datasets/cmu3a4m9t08yfad0djatm1p0z/runs/7e528c95-10e5-4d13-b1be-1a6049198fb9

| metric | value |
|---|---|
| abstention_correct | **0.500** |
| answer_faithfulness | 0.891 |
| answer_relevance | 0.899 |
| citation_correctness | 0.978 |
| context_utilization | 0.584 |

Half of the 12 out-of-scope questions (GitHub Copilot, Windsurf, Claude API
pricing, JetBrains, general Python, older MCP revisions, Kubernetes deploys,
Claude Desktop connectors, LangChain internals...) did not get a clean "the
documentation does not cover this". The high faithfulness/relevance/citation
scores on this set are misleading on their own — this is exactly the failure
Databricks' taxonomy and `failure_mode` were added to catch: a plausible,
well-cited answer built from tangentially related chunks is not a correct
abstention. This is the first confirmed instance of finding #1 in this
report's own list: measurement was previously blind to this failure.

Follow-up: per-item `failure_mode` review in Langfuse (which 6 failed, and how
— did retrieval hand back tangentially related chunks that the generator then
answered from, or did the model answer from its own knowledge despite the
prompt's "documentation only" instruction). Feeds directly into finding #4a
(rerank in search_docs) and the contextual-prefix work (finding #2): if
retrieval returns weakly related chunks for these off-corpus questions, a
better-labelled index may reduce false "relevant" hits at the retrieval stage
before the generator ever sees them.

### Negative set — item-level review (all 12 traces pulled from Langfuse API)

The aggregate `abstention_correct = 0.500` breaks down into three different
things, not one problem. Pulled every trace's question, sources and full
answer via `lf.api.datasets.get_run` + `lf.api.trace.get` (categorical scores
live in `Score.string_value`, not `Score.value` — the first read of this data
misread `failure_mode` as `0.0` for that reason).

**1. Real generator bug — fabricated citation (1 case).** "How do I write
custom instructions for GitHub Copilot in VS Code?" got: *"The provided
documentation identifies this as the location for Copilot rules. [5]"* where
[5] is `code.claude.com/docs/en/memory.md`, which never mentions Copilot. The
corpus does not cover Copilot at all; the model attributed a specific claim to
a real citation that does not support it. `answer_faithfulness` scored 0.86 —
the judge did not catch this. Worth a follow-up: is this systematic (the
generator inventing a citation when no chunk actually answers the question)
or a one-off on a short context?

**2. Real retrieval bug — five identical-document chunks (1 case).** "What
does Claude Opus cost per million input tokens on the API?" retrieved five
chunks, **all from `hooks.md`** (Hooks reference), because it contains a dollar
figure in an unrelated caching example ($1.1396 / 182,340 tokens). The model
derived "~$6.25/million" from that figure via arithmetic and presented it as
an estimate. This is a concrete, reproducible instance of the "crowding"
finding from the earlier audit (finding #4 / `rag-findings.md` §7.6): one
document occupying the whole context. `MAX_CHUNKS_PER_SECTION = 2`
(`context_selector.py`) caps chunks per *section*, not per *document* — this
query needed a per-document cap or a relevance floor instead.

**3. Dataset error, not a system failure (1 case, fixed).** "How do I add a
custom connector in the Claude desktop app settings?" was labelled negative,
but `code.claude.com/docs/en/mcp.md` documents
`claude_desktop_config.json` and the `mcpServers` key directly — the system's
answer was correct and well-cited. Replaced with `launchdarkly-feature-flags`
in `evals/negative_cases.py`; the stale Langfuse item was deleted via the API
(`dataset_items.delete`) so it does not resurface in the next run.

**4. Debatable by design, not by fact (3 cases).** Python decorator caching,
OpenAI fine-tuning, and Kubernetes Helm deployment all got answers that
*explicitly* separate documented fact from general knowledge ("This example
is a recommendation, not behavior specified by the provided MCP
documentation"). `abstention_correct` scores these as wrong because they are
not a clean refusal, but they are not fabrication either — `answer.txt`
currently allows recommendations built on outside knowledge as long as they
are labelled, and the generator did label them. Whether that is the wanted
product behaviour for an MCP tool (a coding agent may want the honest
"not documented" without the improvised scaffold) is a product decision, not
a bug; the metric is working as designed, just stricter than "reasonable
hedged answer."

**Net:** of 6 measured misses, 1 is a real generator faithfulness bug, 1 is a
real retrieval distractor bug (both worth fixing), 1 was a dataset labelling
error (fixed), and 3 are policy questions the abstention metric surfaces but
does not itself resolve. `precision@k`/`ndcg@10` and the retrieval-only curve
above are unaffected by any of this — they come from a separate, already
correct dataset.

## Fixes applied and verified — 2026-09-16

Both real bugs from the item-level review were fixed and re-measured on the
same negative set.

**Fabricated citation (generator).** `_format_context` now renders a
`Product: vendor/product` line per chunk; `answer.txt` and
`answer-evaluator.txt` (published as prompt version 4) require a citation's
Product label to match the product named in the question. The exact
regression case — GitHub Copilot answered by citing a Claude Code
`memory.md` section as "the location for Copilot rules" — now abstains
cleanly and correctly separates the two products.

**Context crowding (retrieval).** `select_generation_context` gained
`min_rerank_score` (default `0.35`, from `src.config.settings`), applied
before either selection pass; wired into `generate_answer`, `iterative.py`,
and the eval harness. On the exact regression case (Claude Opus API pricing)
the retrieved context dropped from 5 duplicate `hooks.md` chunks
(scores 0.28-0.53) to 2 (0.38-0.53), and the fabricated "~$6.25/million"
derived estimate is gone — the answer now cleanly states the cache-write
figure cannot be used to derive the input-token rate. This does not count as
a metric win (`abstention_correct` wants a flat refusal, not an answer that
engages with a weakly-related chunk), which is the same "debatable by
design" category as three other cases in the first review, not a bug.

Fixing #2 surfaced a real measurement bug of its own: the eval script applied
`select_generation_context` twice (once for reporting, once inside
`generate_answer`), so the recorded context diverged from what the generator
actually saw, and `answer_quality_metrics` zeroed every score whenever
`min_rerank_score` filtered candidates to empty — even when the resulting
canned "I couldn't find relevant documentation" reply was a correct
abstention, not a failure. Both fixed (single selection; only a missing
answer, not empty context, short-circuits scoring) before trusting the
numbers below.

| metric | before | after |
|---|---|---|
| abstention_correct | 0.500 (6/12) | **0.833 (10/12)** |
| answer_faithfulness | 0.891 | 0.974 |
| citation_correctness | 0.978 | 0.982 |
| context_utilization | 0.584 (measurement artifact) | 0.777 |
| answer_relevance | 0.899 | 0.632 (expected: a flat refusal is by definition less "relevant" to the literal question than a hedged answer) |

Remaining 2 misses: Claude Opus pricing (bug fixed; metric strictness, see

review — needs its own look before concluding anything, likely the same
"engages instead of refusing" pattern given the retrieval floor left it 5
weakly-scored chunks rather than 0).
